# 批小智 WebApp 功能与交互验收报告

## 1. 验收结论

本次验收不能判定 WebApp 已经“全部正常运行”。

在生产预览环境中，登录、班级/学生维护、批次创建、批量上传、试卷文件上传、OCR Worker 任务、学生归属、校对确认以及 PDF/Word 报告生成均可以走通；但核心的“识别结果展示 → 答案确认 → 发起批改 → 教师复核 → 正式成绩”没有闭环。

最严重的问题是：后端数据库已经生成 OCR 文本块，但前端校对页面仍显示“当前页面还没有可用 OCR 文本块”，导致识别结果无法用于题干和学生答案回填。随后批改入口又因答案覆盖记录不完整、模型服务配置不完整而阻断。

建议先修复 OCR 数据契约和批改前置校验，再进行正式试用或演示验收。

## 2. 验收范围与样本

- 浏览器：Codex 内置浏览器，访问 `http://localhost:4174/`。
- 后端：本地 FastAPI 服务，健康检查返回 200。
- 前端构建：`npm run build` 通过。
- 验收批次：`功能验收-数学面积题-20260920`。
- 验收班级：`功能验收班-20260920`。
- 学生：林晨、陈悦、周宁、许言（本次验收自拟姓名）。
- 文件：4 张学生作业图片 + `答案.jpg` 作为 `question_paper` 试卷/题干来源。
- 题目：6 题，总分 100 分；其中 2 题客观题、4 题主观题，主观题绑定了数学评分标准版本。

`答案.jpg` 本身不是干净的标准答案页，画面中包含手写过程、批注和背景中的其他表格/姓名信息。因此它适合验证上传和 OCR 流程，不适合作为识别准确率的正式基准。

本次未删除验收数据和上传文件，以便继续复现；没有确认任何删除操作。

## 4. 关键问题与风险

### P1-01：OCR 文本块已写入后端，但前端取错字段，校对页面显示为空

事实：试卷页和 4 张学生页的 OCR Worker 任务均为 `succeeded`，数据库中实际存在文本块：

- `答案.jpg`：125 个 OCR 文本块；
- 4 张学生页：分别为 116、82、96、94 个 OCR 文本块。

但内置浏览器中的试卷校对区和学生校对区均显示“当前页面还没有可用 OCR 文本块”，学生答案也没有自动回填。

推理：后端详情接口把带文本块的数据放在 `ocr_runs[].blocks`，前端却直接读取 `latest_ocr_run.blocks`。这是前后端响应结构不一致，不是单纯 OCR 识别失败。

风险：教师看不到 OCR 结果，无法选择文本块加入题干，也无法校对学生答案；当前“succeeded”状态会给人错误的完成感。

优化：统一 API 契约。建议由后端在 `latest_ocr_run` 中直接返回 `blocks`，或由前端统一从 `ocr_runs` 读取；同时增加接口契约测试，至少覆盖“任务 succeeded 且 blocks 非空”的响应。

### P1-02：页面确认成功，但答案覆盖记录不完整，批改入口仍被阻断

事实：4 个学生作业对象和页归属均已确认，页面也提示“当前页面已确认”。但数据库只生成了 1 条 `question_answers` 记录，即验收批次中只有一个学生的一道题有已确认答案。

推理：空题、未定位题目或未编辑题目没有形成明确的“空题已确认/未作答已确认”记录；页面级确认状态与题目级答案覆盖状态不一致。

风险：教师以为页面确认完成后可以批改，实际发起批改时才被后端拒绝，且页面只显示笼统的“未满足前置条件”。

优化：

1. 页面确认时为每个学生×题目生成明确的覆盖状态：已作答、确认空题、待校对、缺失。
2. 发起批改前展示可操作的阻断清单，例如“林晨：第 1、3、4、5、6 题未确认”。
3. 不允许“页面确认成功”掩盖题目级答案仍未完成的事实。

### P1-03：批改前置条件没有向教师解释具体原因

本次发起批改至少存在两类阻断：答案覆盖记录未完整确认，以及设置页显示模型配置仍为“待配置”，Base URL 和服务端 API Key 引用为空。智能批改页面只显示“当前批次尚未满足发起批改的前置条件”，没有展示具体错误码和修复入口。

优化：将后端校验结果逐项展示，并提供“去 OCR 校对”“去设置配置模型”“查看缺失答案”等直接入口；发起按钮在前置校验未通过时显示禁用原因，而不是点击后才出现通用错误。

### P1-04：主观题照片识别接口返回 500，页面只有泛化错误

事实：在已保存学生归属的页面中，选择一张答案图片，点击“识别照片并回填”，页面显示“请求失败（500）”和“识别失败”。

风险：主观题照片识别是 OCR 结果不可用时的备用路径，但当前备用路径也不可用，且教师拿不到可定位的错误原因。

优化：先在后端日志和接口响应中定位 500 根因；前端展示任务 ID、失败阶段、可重试按钮和可回退到手动录入的提示。500 时不要只显示“请求失败”。

### P1-05：批次创建页没有实现“上传图片后一键添加题目”的目标交互

事实：创建批次弹窗中只有手动添加题目和题型/分值/评分标准配置；图片上传与“一键识别题型”位于独立的 OCR 校对页面，不能在创建批次页面直接上传图片并自动生成题目配置。

风险：这与期望的产品交互不一致，用户会误以为 OCR 页面就是创建题目的入口，流程被拆成两个没有明确衔接的页面。

优化方向：在创建批次页增加“从试卷图片识别题目”入口，上传后完成题目分段、题号、题型、题干草稿和分值草稿生成；识别结果必须经过教师确认后再写入批次配置。OCR 页面可以保留为后续校对页，但不应作为唯一入口。

### P1-06：开发模式首页请求超时，生产预览却正常

事实：`npm run dev` 进程可以输出 Vite ready，但对 `http://127.0.0.1:5173/` 的请求在 5 秒内超时；生产构建和 `http://127.0.0.1:4174/` 预览均正常。

风险：开发人员可能误以为服务已启动，实际浏览器无法打开首页；问题会被误判成后端登录故障。

优化：检查 Vite 开发服务器的 HTML fallback、HEAD 请求处理、端口占用和并行启动的旧 Node 进程；增加启动后的健康检查脚本，只有首页可在限定时间返回 200 才提示启动成功。

### P2-01：删除入口语义不一致，已上传批次仍显示“删除草稿批次”

事实：验收批次已经保存 4 张学生图片和 1 张试卷图片，但作业管理列表仍出现“删除草稿批次”按钮。点击后浏览器确认框文案又说明“仅会删除未上传文件的草稿批次”。本次没有确认删除，因此数据未被删除。

风险：用户会误以为可以删除错误批次；确认后可能得到 409 错误，或误以为删除成功但批次仍在。

优化：

- 草稿且无文件：显示“删除草稿”；
- 已上传或 OCR 中：显示“撤销并删除批次”，明确说明会删除文件、页面和 OCR 缓存；
- 已进入批改/复核/报告：隐藏删除，显示“已锁定”及原因；
- 删除按钮与后端可执行条件保持一致，不要让不可执行按钮出现在可点击位置。

### P2-02：OCR 任务进度对试卷和学生作业不一致

试卷 OCR 能显示 0/1、0% 到 1/1、100%；学生批次 OCR 只显示“已入队，请 Worker 完成后刷新页面”，4 页完成后才变为 succeeded，没有总进度、已完成页数或失败页数。

优化：统一显示任务状态、总页数、已完成页数、失败页数、当前阶段和最后更新时间；学生 OCR 应自动轮询或使用服务端推送，不应要求教师凭经验刷新。

### P2-03：OCR 结果噪声和异常没有被前端可见地处理

`答案.jpg` 含背景表格、手写批注和多种非题干内容，OCR 产生了大量低置信度或混杂文本块。后端虽然保存了置信度，但前端当前看不到文本块，也就无法进行异常筛选。

优化：显示置信度和异常标签，支持按页面区域/题号筛选；对背景表格、姓名区、批注区增加裁剪或版面区域识别；对低置信度题干要求教师确认后才允许绑定。

### P2-04：没有真实评分结果时仍可生成空的正式报告

事实：在 0 份参与批改、4 份待复核的情况下，PDF 和 Word 导出都能排队并生成文件，报告内容统计为 0 人、平均分为空。

风险：教师可能把空报告当成正式成绩报告发送或归档。

优化：导出前明确区分“预览空报告”和“正式报告”；没有任何已复核学生时，正式报告按钮应禁用，或必须二次确认并在文件标题/页眉标注“无正式成绩”。

### P2-05：评分标准目前仍是自然语言整体描述，部分得分可解释性不足

当前评分标准可以保存、启用和绑定，但真实批改未能执行，因此尚未验证“完整答案满分、部分完成按比例给分”的实际效果。仅依赖一段自然语言评分说明，容易出现同类答案给分不一致。

优化：评分标准改为结构化评分点：评分点名称、满分、部分得分条件、常见错误、可接受等价表达、证据要求；自然语言说明作为补充提示，不作为唯一可执行规则。批改结果中展示命中的评分点及扣分依据。

## 5. 建议修复顺序

### 第一优先级：先恢复真实批改闭环

1. 修复 `latest_ocr_run.blocks` 与 `ocr_runs[].blocks` 的前后端字段契约。
2. 为每个学生×题目建立明确的答案覆盖状态，并在 UI 展示缺口。
3. 补充模型服务配置校验和可见的阻断详情。
4. 修复主观题照片识别 500，并保留可用的手动录入回退。
5. 用一份干净试卷图和至少两份学生作业重新跑通：OCR 文本显示、题干绑定、答案确认、批改任务、教师复核、报告统计。

### 第二优先级：修正高频交互

1. 重做批次删除/撤销入口的状态语义。
2. 为学生 OCR 增加真实进度和自动刷新。
3. 空报告增加拦截和明确标识。
4. 创建批次页补齐图片识别添加题目的入口和流程衔接。

### 第三优先级：提升准确性与可解释性

1. 引入题干/学生答案区域裁剪和异常检测。
2. 评分标准结构化，支持部分得分和等价答案。
3. 增加接口契约测试、Worker 集成测试和一条真正的浏览器 E2E 测试；不要只测试独立静态原型或 localStorage 数据。

## 6. 验收边界

本次结果证明“上传、任务入队、Worker 执行、数据持久化和部分页面交互”可以运行，但不能证明 OCR 识别质量、模型批改质量或评分公平性。原因是：

- OCR 结果虽已落库，前端无法展示和校对；
- 批改任务没有成功入队；
- 模型 API 配置未完成；
- 样本只有 4 份学生作业，且 `答案.jpg` 不是干净标准答案页。

因此当前版本更适合继续修复和联调，不适合宣称“整条 AI 自动批改流程已验收通过”。
